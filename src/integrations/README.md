# Supabase и онлайн-запись

## Настройка Vercel

Node.js 22.x или 24.x. Framework preset: Vite; build `npm run build`, output `dist`.
Vercel автоматически разворачивает `api/bookings.ts` как Node Serverless Function.
`vercel.json` задаёт maxDuration 30 секунд. Нельзя публиковать только dist на
статическом хостинге: там серверный API отсутствует.

Переменные проекта (для каждого нужного окружения Vercel):

| Переменная | Назначение |
| --- | --- |
| VITE_SUPABASE_URL | Публичный URL Supabase для каталога |
| VITE_SUPABASE_PUBLISHABLE_KEY | Только publishable key для каталога |
| SUPABASE_URL | Тот же URL, серверная конфигурация |
| SUPABASE_SECRET_KEY | Секретный Supabase key, только сервер |
| BOOKING_ALLOWED_ORIGIN | Точный origin сайта, например https://cut.example, без завершающего / |
| UPSTASH_REDIS_REST_URL | HTTPS REST URL отдельной Upstash Redis базы |
| UPSTASH_REDIS_REST_TOKEN | Секретный REST token Redis, только сервер |

После установки переменных выполнить redeploy. Preview имеет другой origin:
задайте соответствующее значение в его окружении, не разрешайте произвольный
Origin или wildcard. Не отдавайте production secrets недоверенным preview-веткам.
Локальные секреты — только в игнорируемом `.env.local`. Для запуска API локально
нужен `vercel dev`; `npm run dev` и preview запускают только Vite.

Никогда не помещать секретные ключи в VITE_*, клиентские файлы, Git или логи.
Не включать логирование тела запроса/телефонов в Vercel, Supabase и внешних прокси.

## Проверить базу перед запуском

Схема каталога соответствует переданной структуре. Клиент использует только
публичный SELECT barbers/services. RLS bookings остаётся закрытым для публичных
INSERT/SELECT; миграций и новых политик нет. Серверный ключ обходит RLS и должен
быть доступен исключительно функции.

В Supabase SQL Editor администратор должен проверить существующее ограничение:

```sql
select pg_get_constraintdef(oid)
from pg_constraint
where conrelid = 'public.bookings'::regclass
  and conname = 'bookings_no_overlap';
```

Убедиться, что это exclusion constraint для одного barber_id и пересечения
интервалов starts_at/ends_at, предикат включает status = 'confirmed', а соседние
интервалы [start,end) разрешены. Проверить, что статус confirmed допустим.
Не пересоздавать ограничение и не ослаблять RLS. Без этой проверки нельзя
подтверждать защиту от гонок на реальной базе.

## POST /api/bookings

Только same-origin JSON, поля barber_id, service_id (int8 ID числом в безопасном
диапазоне или десятичной строкой), starts_at (UTC ISO, например
2026-11-17T07:00:00.000Z), client_name (2–100 символов), client_phone
(международный номер с +; российская 8 нормализуется в +7).
Другие поля, в том числе ends_at/status, отклоняются. Лимит тела 4 КиБ.
Сервер заново читает мастера и длительность услуги, вычисляет ends_at,
проверяет будущее время до 180 дней и 10:00–22:00 Europe/Moscow (UTC+03:00).
Сохраняет confirmed. Отпуска/индивидуальные расписания не моделируются
существующей схемой: сейчас все мастера работают в общие часы.

Успех: 201 {"saved":true} только после успешного INSERT. SQLSTATE 23P01 → 409.
Остальные ответы: 400 валидация/недоступный каталог, 403 origin, 405 метод,
413 размер, 415 формат, 429 лимит, 503 конфигурация/инфраструктура/ошибка БД.
Нет SELECT bookings, передачи клиенту деталей БД, PII других записей или кеширования.

Предварительной SELECT-проверки занятости нет: она не защищает от гонки.
Конфликт разрешает существующее ограничение PostgreSQL при INSERT. Отдельного
API свободных слотов пока нет: форма позволяет выбрать желаемое время, затем
сервер либо сохраняет его, либо сообщает о конфликте.

## Спам и повторные запросы

Redis EVAL атомарно ограничивает 5 попыток/IP за 10 минут во всех инстансах.
При недоступном Redis/конфигурации запись закрыта (503). IP хранится как HMAC
с TTL, без открытого IP. Доверяем только заголовку x-forwarded-for,
перезаписываемому входным прокси Vercel. Вне Vercel нужно отдельно настроить
доверенную границу прокси; нельзя принимать клиентский forwarded header напрямую.
Origin предотвращает браузерные cross-origin запросы, но не заменяет защиту от
ботов. Для продакшена дополнительно рекомендуется Vercel Firewall rate limit
на /api/bookings и Turnstile при необходимости: распределённые боты обходят IP-лимит.

Форма блокирует двойной клик, не повторяет запрос автоматически и показывает
успех только при 201/saved:true. При сетевом сбое запись могла сохраниться:
показывается неопределённость, нужно уточнить её у салона. Полной идемпотентности
пока нет; повтор того же интервала получит 409 за счёт exclusion constraint.
Не менять время и не пересылать запись автоматически после timeout.

## Проверки

`npm test`: валидация, int8, телефон, Moscow/UTC, часы/горизонт, серверная
длительность/статус, ошибки БД, 409, параллельные запросы (mock), rate-limit,
отказ при недоступном Redis и проверки метода/origin/размера.
`npm run build`: TypeScript клиента, API и тестов плюс Vite production build.

Без серверных переменных Codex не проверяет настоящую запись, Redis и определение
ограничения. После deployment провести контролируемую запись с тестовыми данными,
проверить строку администратором, отправить два одновременных запроса на один
интервал (один 201, один 409), затем удалить тестовые данные через защищённый
административный доступ. Проверить отсутствие доступа anon к bookings.
