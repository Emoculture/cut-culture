# Supabase и онлайн-запись

## Настройка Vercel

Node.js 22.x или 24.x. Framework preset: Vite; build `npm run build`, output `dist`.
Vercel автоматически разворачивает `api/bookings.ts` как Node Serverless Function.
`vercel.json` задаёт maxDuration 30 секунд. Нельзя публиковать только dist на
статическом хостинге: там серверный API отсутствует.

Переменные проекта (для каждого нужного окружения Vercel):

| Переменная | Назначение |
| --- | --- |
| VITE_SUPABASE_URL | Публичный URL Supabase для каталога |
| VITE_SUPABASE_PUBLISHABLE_KEY | Только publishable key для каталога |
| SUPABASE_URL | Тот же URL, серверная конфигурация |
| SUPABASE_SECRET_KEY | Секретный Supabase key, только сервер |
| BOOKING_ALLOWED_ORIGIN | Точный origin сайта, например https://cut.example, без завершающего / |
| UPSTASH_REDIS_REST_URL | HTTPS REST URL отдельной Upstash Redis базы |
| UPSTASH_REDIS_REST_TOKEN | Секретный REST token Redis, только сервер |

После установки переменных выполнить redeploy. Preview имеет другой origin:
задайте соответствующее значение в его окружении, не разрешайте произвольный
Origin или wildcard. Не отдавайте production secrets недоверенным preview-веткам.
Локальные секреты — только в игнорируемом `.env.local`. Для запуска API локально
нужен `vercel dev`; `npm run dev` и preview запускают только Vite.

Никогда не помещать секретные ключи в VITE_*, клиентские файлы, Git или логи.
Не включать логирование тела запроса/телефонов в Vercel, Supabase и внешних прокси.

## Проверить базу перед запуском

Схема каталога соответствует переданной структуре. Клиент использует только
публичный SELECT barbers/services. RLS bookings остаётся закрытым для публичных
INSERT/SELECT; миграций и новых политик нет. Серверный ключ обходит RLS и должен
быть доступен исключительно функции.

В Supabase SQL Editor администратор должен проверить существующее ограничение:

```sql
select pg_get_constraintdef(oid)
from pg_constraint
where conrelid = 'public.bookings'::regclass
  and conname = 'bookings_no_overlap';
```

Убедиться, что это exclusion constraint для одного barber_id и пересечения
интервалов starts_at/ends_at, предикат включает status = 'confirmed', а соседние
интервалы [start,end) разрешены. Проверить, что статус confirmed допустим.
Не пересоздавать ограничение и не ослаблять RLS. Без этой проверки нельзя
подтверждать защиту от гонок на реальной базе.

## POST /api/bookings

Только same-origin JSON, поля barber_id, service_id (int8 ID числом в безопасном
диапазоне или десятичной строкой), starts_at (UTC ISO, например
2026-11-17T07:00:00.000Z), client_name (2–100 символов), client_phone
(международный номер с +; российская 8 нормализуется в +7).
Другие поля, в том числе ends_at/status, отклоняются. Лимит тела 4 КиБ.
Сервер заново читает мастера и длительность услуги, вычисляет ends_at,
проверяет будущее время до 180 дней и 10:00–22:00 Europe/Moscow (UTC+03:00).
Сохраняет confirmed. Отпуска/индивидуальные расписания не моделируются
существующей схемой: сейчас все мастера работают в общие часы.

Успех: 201 {"saved":true} только после успешного INSERT. SQLSTATE 23P01 → 409.
Остальные ответы: 400 валидация/недоступный каталог, 403 origin, 405 метод,
413 размер, 415 формат, 429 лимит, 503 конфигурация/инфраструктура/ошибка БД.
Нет SELECT bookings, передачи клиенту деталей БД, PII других записей или кеширования.

Предварительной SELECT-проверки занятости нет: она не защищает от гонки.
Конфликт разрешает существующее ограничение PostgreSQL при INSERT. Отдельного
API свободных слотов пока нет: форма позволяет выбрать желаемое время, затем
сервер либо сохраняет его, либо сообщает о конфликте.

## Спам и повторные запросы

Redis EVAL атомарно ограничивает 5 попыток/IP за 10 минут во всех инстансах.
При недоступном Redis/конфигурации запись закрыта (503). IP хранится как HMAC
с TTL, без открытого IP. Доверяем только заголовку x-forwarded-for,
перезаписываемому входным прокси Vercel. Вне Vercel нужно отдельно настроить
доверенную границу прокси; нельзя принимать клиентский forwarded header напрямую.
Origin предотвращает браузерные cross-origin запросы, но не заменяет защиту от
ботов. Для продакшена дополнительно рекомендуется Vercel Firewall rate limit
на /api/bookings и Turnstile при необходимости: распределённые боты обходят IP-лимит.

Форма блокирует двойной клик, не повторяет запрос автоматически и показывает
успех только при 201/saved:true. При сетевом сбое запись могла сохраниться:
показывается неопределённость, нужно уточнить её у салона. Полной идемпотентности
пока нет; повтор того же интервала получит 409 за счёт exclusion constraint.
Не менять время и не пересылать запись автоматически после timeout.

## Проверки

`npm test`: валидация, int8, телефон, Moscow/UTC, часы/горизонт, серверная
длительность/статус, ошибки БД, 409, параллельные запросы (mock), rate-limit,
отказ при недоступном Redis и проверки метода/origin/размера.
`npm run build`: TypeScript клиента, API и тестов плюс Vite production build.

Без серверных переменных Codex не проверяет настоящую запись, Redis и определение
ограничения. После deployment провести контролируемую запись с тестовыми данными,
проверить строку администратором, отправить два одновременных запроса на один
интервал (один 201, один 409), затем удалить тестовые данные через защищённый
административный доступ. Проверить отсутствие доступа anon к bookings.

## Диагностика HTTP 400

В старом обработчике не было console-вызовов: HTTP 400 присутствовал в Request
Logs, но отдельные Function Logs могли быть пустыми. Это не доказывает, что
конкретный запрос дошёл до обработчика: отклонения инфраструктуры тоже возможны.

Теперь ответ приложения содержит безопасный `code`, а заголовок `X-Request-ID`
содержит новый серверный UUID. В Function Logs пишется только JSON:
`event=booking_rejected`, `status=400`, `code`, `request_id`.
Не логируются тела, значения полей, имена, телефоны, IP, даты записи, токены,
заголовки или объекты исключений. Нельзя включать отладочное логирование payload.

Все причины 400 в обработчике:

| code | Причина |
| --- | --- |
| INVALID_BODY | JSON не является объектом (включая null/массив/строку) |
| UNEXPECTED_FIELDS | Переданы лишние поля, например ends_at или status |
| INVALID_BARBER_ID | ID не положительный int8: неверный тип, дробь, пустая строка, выход за диапазон/безопасность JS |
| INVALID_SERVICE_ID | Те же правила ID для услуги |
| INVALID_NAME | Не строка, короче 2/длиннее 100 после trim, управляющие/невидимые format-символы |
| INVALID_PHONE | Неверный тип, длина/символы или номер вне допустимого формата |
| INVALID_STARTS_AT | Не UTC ISO с минутной точностью, отсутствие Z или невозможная календарная дата |
| START_IN_PAST | Начало не в будущем по серверным часам |
| START_TOO_FAR | Начало позже текущего времени +180 суток |
| OUTSIDE_WORKING_HOURS | Начало раньше 10:00 или окончание позже 22:00 по Москве |
| BARBER_UNAVAILABLE | Сервер не нашёл мастера по ID |
| SERVICE_UNAVAILABLE | Сервер не нашёл услугу по ID |

Неверная длительность в каталоге — 503, конфликт — 409, Redis-лимит — 429;
они не являются ветками 400. RLS, Redis и проверка конфликтов сохранены.

Форма отправляет ровно barber_id/service_id (строки из select), starts_at
(UTC ISO), client_name, client_phone. Дата и время отдельными полями не отправляются.
10:00 по Москве = 07:00Z независимо от часового пояса посетителя. Числовые
безопасные ID тоже принимаются сервером; int8 вне точности JS нужно передавать строкой.

Воспроизведённые несовпадения старой формы и API: форма позволяла телефон с
неразрывными пробелами/номер 7XXXXXXXXXX без плюса и дату дальше 180 дней,
а сервер их отклонял. Теперь общая клиентская/серверная валидация нормализует
российские 7/8 в +7, типографские пробелы и дефисы; невалидные имена/телефоны
показывают точную ошибку до отправки. Горизонт 180 дней проверяется и клиентом.
Произвольные буквы/управляющие символы в телефоне по-прежнему отклоняются.

Причина конкретного production-запроса пока НЕ подтверждена. После redeploy:

1. Проверить, что Vercel развернул актуальный commit main.
2. В Network взять только HTTP status, ответ code и X-Request-ID. Не пересылать
   payload, имя/телефон или ключи. Сопоставить UUID с booking_rejected в Logs.
3. Если BARBER_UNAVAILABLE/SERVICE_UNAVAILABLE, проверить администратором наличие
   выбранных ID в базе сервера и совпадение проектов SUPABASE_URL и
   VITE_SUPABASE_URL. Не выводить ключи для сравнения и не отключать RLS.
4. Если 400 без X-Request-ID/booking_rejected на новом deployment, проверить,
   не отклонён ли запрос до вызова функции: JSON-парсер, маршрутизация или Firewall.
   Вручную повреждённый JSON может быть отклонён Vercel до пользовательского кода.
   Нормальная форма отправляет JSON.stringify с application/json.

В Codex реальный production payload, ответ и Function Logs недоступны. Тесты
проверяют локальную валидацию и тестовый repository; реальных записей не создают.

Подробная диагностика серверных 503 и шаги проверки Production Vercel:
[server/README.md](../../server/README.md). Новых переменных для логирования нет.

## Telegram-уведомления владельцу

В Vercel Environment Variables добавьте **только серверные** переменные:

- `TELEGRAM_BOT_TOKEN` — токен бота от BotFather.
- `TELEGRAM_OWNER_CHAT_ID` — числовой ID личного чата владельца (или закрытой группы).

Не используйте префикс VITE_, не добавляйте реальные значения в Git или клиентский
код. В `.env.example` присутствуют только пустые имена переменных. Владелец должен
начать диалог с ботом командой /start; для группы добавить бота с правом отправки.
Получите ID чата доверенным способом, не публикуя вывод getUpdates с персональными
данными. Укажите значения для нужного окружения Vercel и выполните **Redeploy**.
Preview не должен отправлять реальные клиентские данные в production-чат:
используйте отдельного тестового бота/чат или оставьте переменные пустыми.

После успешного INSERT confirmed сервер читает name мастера и услуги из Supabase
по проверенным ID, затем вызывает Telegram sendMessage. Имя клиента и телефон
берутся из уже провалидированных данных записи. Названия из JSON клиента не
принимаются. В сообщении: имя, телефон, услуга, мастер, дата и интервал по Москве
(Europe/Moscow, UTC+03:00). Формат — обычный текст без parse_mode; предпросмотр
ссылок отключён. Клиентский интерфейс и успешный ответ API не меняются.

Серверному доступу нужен SELECT name для barbers и services, помимо существующих
чтений id/duration_minutes. Если прав нет, запись сохраняется, а уведомление
логируется как TELEGRAM_CATALOG_FAILED. Никаких grants, SQL или RLS-изменений
этот коммит не выполняет.

Бюджет lookup+send — 4 секунды, операция ожидается внутри serverless invocation.
Клиентский таймаут увеличен до 28 секунд с учётом существующих серверных
таймаутов и дополнительной отправки; лимит функции Vercel остаётся 30 секунд.
Если отсутствуют переменные, Telegram недоступен, отказывает или возвращает
некорректный ответ, сохранённая запись остаётся успешной (201/saved:true).
Обновлять запись, удалять её или повторять INSERT из-за Telegram нельзя.
Для failed/409/429/неподтверждённого INSERT отправки нет.

Runtime Logs: событие `booking_notification_failed`, фиксированный код и серверный
request_id. Коды: TELEGRAM_CONFIG_MISSING/CONFIG_INVALID, TELEGRAM_CATALOG_FAILED,
TELEGRAM_TIMEOUT/NETWORK_FAILED/HTTP_FAILED, TELEGRAM_RESPONSE_INVALID/REJECTED,
TELEGRAM_UNEXPECTED_FAILURE. Токен, chat_id, URL с токеном, тело/ответ Telegram,
имена и телефоны в лог не попадают. Системы внешнего трассирования тоже не должны
записывать URL/тела запросов к Bot API. Доступ к чату ограничьте владельцем:
уведомление намеренно содержит данные клиента.

Это best-effort доставка без очереди и автоматических повторов. При обрыве связи
Telegram мог принять сообщение; сервер не пересылает его повторно, чтобы не
дублировать. При аварийной остановке функции после сохранения уведомление может
не дойти. Для гарантированной доставки нужен отдельный transactional outbox.
Наличие уведомления не заменяет базу как источник подтверждённых записей.

Локальные тесты используют фиктивные токены/ID и подменённый fetch. Реальные
сообщения и записи в production при проверке не создаются. После настройки и
redeploy проверить уведомление на согласованной тестовой записи.

## Команда владельца /today

Webhook: **https://cut-culture.vercel.app/api/telegram-webhook**.
Отдельная Vercel Serverless Function; существующие /api/bookings и уведомления
не изменены. Никаких новых публичных политик или SQL-изменений нет.

В Vercel Production добавить `TELEGRAM_WEBHOOK_SECRET`: отдельный случайный секрет
(рекомендуется 32+ символа; допустимы A-Z, a-z, 0-9, _ и -, до 256 символов).
Создать/хранить его в менеджере паролей. Не использовать токен бота в качестве
секрета webhook. Также нужны уже существующие TELEGRAM_BOT_TOKEN,
TELEGRAM_OWNER_CHAT_ID, SUPABASE_URL, SUPABASE_SECRET_KEY. Затем Redeploy.
Серверному ключу нужен SELECT соответствующих колонок bookings, barbers, services;
не предоставлять этот доступ anon/authenticated и не ослаблять RLS.

Команда работает **только в личном чате владельца**. TELEGRAM_OWNER_CHAT_ID должен
быть положительным числовым ID этого чата, совпадающим с Telegram user ID владельца.
Webhook проверяет и chat.id/type, и from.id/is_bot. Группы/каналы не допускаются,
даже если команда пришла от владельца: список содержит клиентские данные.
Существующие уведомления по-прежнему поддерживают их прежние настройки; если они
настроены на группу, для /today потребуется выбрать личный чат владельца в этой
переменной. Другие пользователи/команды/edited updates игнорируются без чтения БД
и без отправки сообщения. Неверный X-Telegram-Bot-Api-Secret-Token даёт 403 до БД.

### Регистрация вручную без раскрытия токена

1. Владелец должен нажать /start в личном чате с ботом.
2. Дождаться успешного Production deployment с настроенными переменными. Endpoint
   должен быть доступен Telegram без Vercel Deployment Protection challenge.
   Доступ к данным защищён секретом webhook и проверкой владельца.
3. На доверенной машине в терминале выполнить:

```sh
python3 scripts/register-telegram-webhook.py
```

Скрипт запросит токен и webhook secret через скрытый ввод getpass. Значения не
попадают в аргументы команды, историю shell или вывод; секрет должен совпадать с
Vercel. Запрос setWebhook содержит url, secret_token, allowed_updates=[message,callback_query],
max_connections=1. Скрипт не вызывается npm build/dev, API или тестами. В Codex
он не запускался и webhook автоматически не регистрировался. У одного бота может
быть один webhook: регистрация заменяет прежний; не использовать параллельно
getUpdates/long polling. Не вводить URL Bot API с токеном в браузер, curl-команду
или логи CI; не включать отладочную трассировку HTTP.

### Расписание и часовой пояс

/today возвращает подтверждённые (status=confirmed) записи, starts_at которых
попадает в [00:00 сегодня, 00:00 завтра) по Москве. Порядок — starts_at по
возрастанию. Поля: время, имя клиента, услуга и мастер. Телефон не выбирается из БД
и не включается в сообщение. Пустой список явно сообщается. Названия услуг/мастеров
загружаются по серверным ID из каталога; удалённые элементы обозначаются заглушкой.

Часовой пояс — **Europe/Moscow (UTC+03:00)**. Для команды он задан константами
TODAY_TIME_ZONE и TODAY_UTC_OFFSET_MINUTES в server/telegram-today.ts.
Переменной окружения часового пояса нет: система бронирования и уведомления также
используют Москву. При смене салона согласованно обновить обе константы и прежнюю
логику бронирования/уведомлений. Расчёт команды предназначен для фиксированного
московского смещения, не является универсальной поддержкой DST.

Выводится максимум 200 записей, с явным предупреждением при превышении. Длинный
список делится на сообщения <4096 символов, текст без Markdown/HTML parse_mode,
предпросмотр ссылок отключён. Длинные имена ограничены 60 символами в выводе.
Между частями выдерживается пауза для лимитов Telegram. Общий deadline — 25 секунд,
функция Vercel — 30. При ошибке возвращается 503 и безопасный лог
telegram_webhook_failed: только фиксированный code и серверный request_id.
Не логируются updates, chat ID, заголовки, тексты ошибок, записи, имена или токены.
Внешняя трассировка также не должна записывать payload/URL с bot token.

Telegram повторяет webhook при сетевых сбоях/неуспешном ответе. Повторная
обработка теперь ограничена общим Redis-захватом update_id; подробности и
ограничения доставки см. в разделе «Все записи и защита от повторных update» ниже.
Записи при просмотре расписания не создаются и не меняются.

### Команда /tomorrow

В том же webhook поддерживается `/tomorrow` (также `/tomorrow@ИмяБота`). Она
показывает подтверждённые записи на следующий **московский календарный день**,
а не на следующие 24 часа от момента запроса и не на завтрашний день UTC сервера.
Границы запроса: [00:00 завтра, 00:00 послезавтра) Europe/Moscow, включая переходы
месяца/года. Сегодня и завтра используют общий код авторизации, расчёта диапазона,
чтения Supabase, сортировки и форматирования. В обеих командах теперь отображается
интервал начала–окончания, имя клиента, услуга и мастер. Пустой завтрашний список:
«На завтра подтверждённых записей нет».

Новых переменных, маршрутов или SQL grants не добавлено. Используются прежние
TELEGRAM_OWNER_CHAT_ID, TELEGRAM_WEBHOOK_SECRET и серверные ключи. Личный чат,
проверка отправителя и секрета сохранены. Системы бронирования и уведомлений не
изменены. Для чтения окончания webhook выбирает существующий столбец ends_at.
Если серверные права ранее были ограничены на уровне колонок, их доступность
проверяет администратор; этот коммит права базы не меняет.

После push нужен deployment/redeploy Vercel. Повторный setWebhook не требуется,
если он уже зарегистрирован на /api/telegram-webhook этого домена. Автоматическая
регистрация/смена webhook и вызовы setMyCommands не выполняются.

## Интерактивное меню владельца

`/start` и `/menu` открывают приветствие с inline-кнопками «📅 Сегодня» и
«📆 Завтра». Они вызывают общую логику `/today` и `/tomorrow`; после расписания
(в том числе пустого) к последней части сообщения добавляется «🏠 Главное меню».
Текстовые команды расписания продолжают работать и тоже показывают кнопку меню.
Данные кнопок — фиксированные schedule:today, schedule:tomorrow, menu:main.
Клиентские даты, названия или ID записей через callback_data не принимаются.

Обрабатывается только обычный callback_query с сообщением в личном чате
владельца и callback_query.from.id владельца. Отправитель сообщения с кнопкой —
сам бот: проверять вместо него нужно именно callback_query.from. Чужие чаты,
чужие отправители, группы, боты и inline callbacks без личного чата игнорируются
до инициализации зависимостей. Секрет webhook проверяется до любого действия.
Авторизованный callback подтверждается answerCallbackQuery **до** чтения БД;
неизвестная кнопка владельца подтверждается без чтения/отправки расписания.
При ошибке подтверждения обработка останавливается с безопасным BOT_CALLBACK_FAILED.
Открытие меню и подтверждение callback не требуют Supabase или запросов к нему.

После deployment необходима **ручная повторная регистрация webhook**: предыдущая
настройка allowed_updates=['message'] не доставляет нажатия inline-кнопок.
На доверенной машине запустить обновлённый скрипт:

```sh
python3 scripts/register-telegram-webhook.py
```

Он передаёт allowed_updates=['message','callback_query'], сохраняя тот же адрес и
secret_token. Токен/секрет вводятся скрыто. Автоматического setWebhook при запуске
или сборке нет; скрипт в ходе разработки не выполнялся. Новых переменных окружения
нет. Права БД, бронирование и уведомления о новых записях не меняются.

Состояние навигации не хранится — действие определяется фиксированным
callback_data. Для защиты от повторных update используется существующий Redis,
см. следующий раздел. Логи содержат только код ошибки и серверный Request ID,
без updates, callback ID, chat ID и данных клиентов.

## Все записи и защита от повторных update

В главном меню добавлена «📋 Все записи», текстовая команда — `/bookings`.
Период — **7 календарных дней по Europe/Moscow, включая сегодня**: от 00:00
сегодня до 00:00 восьмого дня (верхняя граница исключена). Включены все
подтверждённые записи сегодняшнего дня, в том числе уже прошедшие сегодня.
Используются существующий webhook и серверный Supabase-клиент; фильтр confirmed.
Выборка отсортирована starts_at, затем id для устойчивого порядка при совпадении
времени. Телефоны не выбираются. Вывод сгруппирован по датам, показывает интервал
начала–окончания, имя клиента, мастера и услугу. Длинные поля ограничены 60 символами
в сообщении, plain text без parse_mode и предпросмотра ссылок.

Страница — 10 записей; сервер запрашивает 11 строк для определения наличия
следующей страницы. Это заменяет общий лимит 200 только для недельного списка:
/today и /tomorrow сохраняют прежнее поведение. Кнопки «⬅️ Назад», «Вперёд ➡️»,
«🏠 Главное меню». callback_data содержит только фиксированную команду и номер
страницы (0–9999), без имён, телефонов, ID записей или клиентских данных. Пустой
список: «На ближайшие 7 дней записей нет». Если страница опустела после изменения
расписания, предлагается вернуться назад/открыть список заново. Каждая страница
заново читает базу и вычисляет текущий московский период: список живой, без
снимка/кеша PII. В полночь диапазон сдвигается, новые записи могут сдвигать страницы.
Для начала просмотра заново нажать «Все записи» в меню. Максимум — 10000 страниц.

### Повторная доставка

После проверки webhook-секрета, личного owner chat и sender ID, но **до** чтения
базы и отправки сообщений, выполняется атомарный Redis SET NX EX на 7 суток.
Используются существующие UPSTASH_REDIS_REST_URL / UPSTASH_REDIS_REST_TOKEN;
новых переменных нет. Ключ имеет отдельный namespace cut-culture:telegram:update
и HMAC идентификатора update с токеном бота. В значении только маркер claimed,
без PII и текстов сообщений. Несколько serverless-инстансов конкурируют за один
общий ключ: обработку получает только один. Состояние в памяти Vercel не хранится.
Защита применяется к **всем** авторизованным действиям webhook, не к API записи.
Дубликат получает 200 без повторного чтения/отправки/ack. Обычный callback
подтверждается до запроса расписания. При недоступном Redis — 503 и фиксированный
BOT_DEDUP_FAILED; чтений и отправки нет. Бронирование и уведомления не изменены.

Захват сохраняется и при ошибке: сеть могла оборваться уже после принятия
sendMessage Telegram. Это политика **не более одной попытки обработки update**,
а не гарантия ровно одной успешной доставки. При падении функции/сбое Redis после
захвата/ошибке чтения или отправки ответ может не прийти: владелец должен снова
ввести команду или нажать кнопку (новый update_id). Автоматического release/retry
сообщений нет. После истечения TTL или смены bot token старые update не защищены
тем же ключом; это покрывает обычные повторы Telegram, не бессрочный архив.

Redis должен разрешать SET с NX/EX. Права/SQL/RLS не меняются. Администратор
проверяет доступ серверной роли к выбранным колонкам bookings, barbers, services;
публичный доступ не открывается. Функции редактирования/отмены не добавлены.
Секреты и персональные данные не передаются в URL/callback_data и не логируются.
Нужен deployment/redeploy Vercel. Повторный setWebhook не требуется, если уже
разрешены message и callback_query после внедрения меню. Новых переменных нет.

Тесты используют только фиктивные ключи и подменённые Redis/Supabase/Telegram;
реальные сообщения, записи, SQL и регистрация webhook при разработке не выполняются.

## Отмена записи владельцем

Схема подтверждена владельцем через Supabase SQL Editor:
status — text DEFAULT 'confirmed', без CHECK/enum; bookings_valid_time проверяет
ends_at > starts_at; bookings_no_overlap — EXCLUDE USING gist
(barber_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)
WHERE (status = 'confirmed'). Есть PK/FK, пользовательских триггеров нет.
На этой схеме cancelled допустим и не участвует в проверке пересечений.
**Миграция структуры/ограничения не требуется и не выполнялась.**

В «Все записи» строки пронумерованы и снабжены «Открыть запись N». Карточка
показывает клиента, мастера, услугу, дату и интервал по Москве. «Отменить запись»
открывает отдельное подтверждение «Да, отменить» / «Нет, назад». Ни карточка, ни
вопрос-подтверждение БД не меняют. Команды и прежнее меню остаются доступны.

В callback_data нет ID записи или PII — только действие и случайный 128-битный
токен. Redis хранит ID, страницу и фазу view/confirm, без имени/телефона. Ключи
привязаны HMAC к боту и owner chat. Срок view — 20 минут, confirm — 5 минут.
Подтверждение (и отказ) атомарно потребляет confirm-токен через GETDEL. После
«Нет» старая кнопка «Да» уже недействительна. Произвольный ID/токен не позволяет
отменить запись: проверяются владелец, секрет webhook, ticket, фаза, существование
и текущий статус в базе. Дубликаты update блокирует прежний общий Redis guard.
Разные двойные нажатия защищены GETDEL и дополнительно условным UPDATE.

Отмена: PATCH bookings SET status='cancelled' WHERE id=... AND status='confirmed',
с возвратом id/status. Результат проверяется до сообщения об успехе. Если строка
не изменена, сервер отличает not_found, already_cancelled и not_active. DELETE
не используется. Никаких UPDATE других полей, клиентских сообщений, изменения
RLS, anon/authenticated-политик, бронирования или уведомлений о новых записях нет.
Отмена активной записи здесь означает именно status=confirmed, а не проверку
даты: список включает сегодняшний день, в том числе прошедшие часы.

После подтверждённой отмены список перечитывается; уведомление об отмене и
обновлённая страница отправляются одним сообщением. Если обновить список нельзя,
показывается подтверждённый результат БД и предложение открыть список заново.
Ошибка отправки Telegram не откатывает отмену. При неоднозначной сетевой ошибке
UPDATE успех не сообщается: владелец должен открыть карточку и проверить состояние.
Автоматического повторного UPDATE/отправки нет. Лог booking_cancellation_unconfirmed
содержит только фиксированный BOT_CANCEL_FAILED и Request ID, без payload/ID
записи/клиента. Токены действий также не логируются. Redis должен разрешать
существующий SET NX EX и GET/GETDEL; новых env нет.

### Права и запуск

Серверному service_role нужен SELECT уже используемых полей карточки, включая
id/status, и UPDATE status. Проверку прав и необязательную команду см.
`sql/booking-cancellation-permissions.sql`. **Если UPDATE status уже есть, SQL
выполнять не нужно.** Если нет, администратор может отдельно выполнить:

```sql
GRANT UPDATE ON TABLE public.bookings TO service_role;
```

Более узкий достаточный вариант — GRANT UPDATE (status) ON TABLE public.bookings
TO service_role. Не нужны DELETE, новые функции/RPC, таблицы или права
anon/authenticated. Эти команды подготовлены, но в Supabase не выполнялись.
Ограничение bookings_no_overlap не изменялось. В API сайта отдельного запроса
доступности нет: сервер вставляет confirmed и обрабатывает 23P01 как 409.
После смены статуса прежняя строка исключается из GiST-предиката; защита от двух
пересекающихся confirmed остаётся. Read-only списки также фильтруют confirmed.

После push нужен deployment/redeploy Vercel. Webhook и env остаются прежними;
если меню уже работало, setWebhook повторять не нужно.

### Проверка

`npm test`: карточка, явное подтверждение/отказ, повторные нажатия/update,
несуществующая/неактивная/отменённая запись, авторизация, Supabase/Telegram errors,
случайные owner-bound tickets и отсутствие ID/PII в callbacks.
`npm run build`: TypeScript и Vite. Тесты используют фиктивные данные и транспорт.

В отдельном локальном PostgreSQL 17 проверена копия подтверждённого ограничения:
`tests/sql/booking-cancellation.sql`. Проверки SQL: строка сохраняется, повторный
UPDATE меняет 0 строк, слот можно занять после отмены, новое пересечение confirmed
по-прежнему запрещено, соседние [start,end) разрешены, valid_time сохранён.
`tests/sql/booking-cancellation-concurrency.py` проверяет два конкурентных UPDATE:
ровно один меняет строку. Скрипт работает только с одноимённым локальным Docker
контейнером cut-culture-cancel-test. Эти тесты не запускать в Supabase.

**Отмена ещё не проверена на реальной тестовой записи Supabase.** После deployment
администратор должен провести согласованный тест: создать тестовую confirmed,
отменить в боте, проверить status/сохранение строки, повторить кнопку, затем
забронировать тот же интервал и проверить отказ второй пересекающейся confirmed.
Не использовать реальную клиентскую запись для проверки. Доступ владельца и
закрытые RLS-политики проверить отдельно. До этой проверки не считать запуск
отмены полностью подтверждённым.
